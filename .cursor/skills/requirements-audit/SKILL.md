# 需求审计（先讨论，后实现）

## 目标

与用户通过**互相问答**把需求谈清楚，再动手。默认假设：用户这次是来对齐问题，不是来立刻改代码。多轮讨论时以「已澄清需求」摘要为真源，必要时落盘，避免只靠聊天记忆。

## 硬约束

在用户明确说可以开干之前（例如「实现」「按这个做」「写成 plan 并实现」「开干」）：

- **不要**写业务代码、改数据模型/迁移、改配置与提示词、提交 git、创建 PR
- **不要**一上来给大段实现方案或铺开多文件改动列表
- 允许只读探查代码（Grep/Read），用于把问题问准；探查要窄，不要为「了解全仓」扫目录
- **允许**在用户同意后写入/更新需求定稿文档（见「落盘」）；这不算开干

若用户同一条消息里已经写清需求并要求直接实现，可跳过本 skill，按实现任务处理。

## 流程

1. **复述**：用几句话概括你对目标、范围、成功标准的理解；标出你不确定的点。
2. **提问**：每轮只问 **1～2 个**真正卡决策的问题（优先边界、谁用、数据归属、失败态、非目标）。避免问卷式连发。
3. **迭代**：根据回答更新理解；有冲突时指出来，让用户选。若本轮改口或拍板了关键点，在回复里用「已澄清需求」模板给一版**更新后的摘要**（可只改变动项，但须能单独当现状读）。
4. **收束**：当关键歧义已消除（或用户表示够了），再输出完整「已澄清需求」摘要，并问：接下来是继续细化、**落盘定稿**、还是开始实现？

## 「已澄清需求」模板

用简洁列表，不要空话：

```markdown
## 已澄清需求
- **要解决什么**：
- **谁用 / 在什么场景**：
- **范围内**：
- **明确不做**：
- **验收标准**（可观察行为）：
- **风险 / 已知取舍**：
- **仍待决**（若有）：
```

## 落盘（定稿摘要）

聊天里的摘要是过程稿；下列情况应**提议落盘**（先问路径/文件名，用户同意后再写）：

- 用户说「落盘」「写成 plan」「定稿」「记下来」
- 收束时用户准备开干或换会话
- 讨论已多轮且出现明显改口，继续只靠聊天容易丢结论

默认路径：`.scratch/requirements/<简短英文或拼音主题>-requirements.md`（若用户指定 `docs/` 或其他路径，听用户的）。`.scratch/` 已 gitignore，仅本地。文件内容用上面的「已澄清需求」模板；已有文件则**整份更新为最新定稿**，并在文首可加一行「上次更新：YYYY-MM-DD」。

开干时优先让用户（或下一条消息）指向该文件；实现以落盘定稿为准，不以早期聊天回合为准。

## 提问时可对照的维度（按需，勿整表抛出）

心里过一遍与当前需求相关的维度，**只把真正卡决策的问出来**：

- **范围**：改哪条产品线/模块；明确非目标
- **角色与权限**：谁能触发；鉴权/授权方式是否变化
- **数据**：存什么、谁拥有、隔离边界（多租户/多用户）、是否兼容旧数据
- **交互**：同步 vs 异步；要不要实时/流式反馈；失败与重试如何暴露
- **集成**：是否依赖外部服务、队列、定时任务、第三方 API
- **可观测与验收**：日志/指标；怎样算做完（可演示的行为）

若仓库有 `AGENTS.md`、`.cursor/rules` 或领域文档，用它们校正问题，**不要**把文档整段念给用户。

## 语气

直接、短句；先对齐再发挥。不要用「很高兴帮你梳理需求」这类开场。
