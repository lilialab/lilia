# 需求审计（先讨论，后实现）

## 目标

与用户通过**互相问答**把需求谈清楚，再动手。默认假设：用户这次是来对齐问题，不是来立刻改代码。

## 硬约束

在用户明确说可以开干之前（例如「实现」「按这个做」「写成 plan 并实现」「开干」）：

- **不要**写业务代码、改数据模型/迁移、改配置与提示词、提交 git、创建 PR
- **不要**一上来给大段实现方案或铺开多文件改动列表
- 允许只读探查代码（Grep/Read），用于把问题问准；探查要窄，不要为「了解全仓」扫目录

若用户同一条消息里已经写清需求并要求直接实现，可跳过本 skill，按实现任务处理。

## 流程

1. **复述**：用几句话概括你对目标、范围、成功标准的理解；标出你不确定的点。
2. **提问**：每轮只问 **1～2 个**真正卡决策的问题（优先边界、谁用、数据归属、失败态、非目标）。避免问卷式连发。
3. **迭代**：根据回答更新理解；有冲突时指出来，让用户选。
4. **收束**：当关键歧义已消除（或用户表示够了），输出「已澄清需求」摘要，并问：接下来是继续细化、写成 plan，还是开始实现？

## 「已澄清需求」模板

用简洁列表，不要空话：

```markdown
## 已澄清需求
- **要解决什么**：
- **谁用 / 在什么场景**：
- **范围内**：
- **明确不做**：
- **验收标准**（可观察行为）：
- **风险 / 已知取舍**：
- **仍待决**（若有）：
```

## 提问时可对照的维度（按需，勿整表抛出）

心里过一遍与当前需求相关的维度，**只把真正卡决策的问出来**：

- **范围**：改哪条产品线/模块；明确非目标
- **角色与权限**：谁能触发；鉴权/授权方式是否变化
- **数据**：存什么、谁拥有、隔离边界（多租户/多用户）、是否兼容旧数据
- **交互**：同步 vs 异步；要不要实时/流式反馈；失败与重试如何暴露
- **集成**：是否依赖外部服务、队列、定时任务、第三方 API
- **可观测与验收**：日志/指标；怎样算做完（可演示的行为）

若仓库有 `AGENTS.md`、`.cursor/rules` 或领域文档，用它们校正问题，**不要**把文档整段念给用户。

## 语气

直接、短句；先对齐再发挥。不要用「很高兴帮你梳理需求」这类开场。
