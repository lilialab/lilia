# 需求审计（先讨论，后实现）

## 目标

与用户通过**互相问答**把需求谈清楚，再动手。默认假设：用户这次是来对齐问题，不是来立刻改代码。多轮讨论时以「已澄清需求」摘要为真源，必要时落盘。大需求可再拆成可独立验收的小项，落盘后由用户逐项点名开干，便于 review、降低一次改太大的风险。

## 硬约束

在用户明确说可以开干之前（例如「实现」「按这个做」「写成 plan 并实现」「开干」「做第 N 项」）：

- **不要**写业务代码、改数据模型/迁移、改配置与提示词、提交 git、创建 PR
- **不要**一上来给大段实现方案或铺开多文件改动列表
- 允许只读探查代码（Grep/Read），用于把问题问准；探查要窄，不要为「了解全仓」扫目录
- **允许**在用户同意后写入/更新需求定稿与切片清单（见「落盘」「切片」）；这不算开干

若用户同一条消息里已经写清需求并要求直接实现，可跳过本 skill，按实现任务处理。

若已落盘切片清单：用户点名某一项时**只做该项**；不要顺手做后续切片或扩大范围。

## 流程

1. **复述**：用几句话概括你对目标、范围、成功标准的理解；标出你不确定的点。
2. **提问**：每轮只问 **1～2 个**真正卡决策的问题（优先边界、谁用、数据归属、失败态、非目标）。避免问卷式连发。
3. **迭代**：根据回答更新理解；有冲突时指出来，让用户选。若本轮改口或拍板了关键点，在回复里用「已澄清需求」模板给一版**更新后的摘要**（可只改变动项，但须能单独当现状读）。
4. **收束**：当关键歧义已消除（或用户表示够了），再输出完整「已澄清需求」摘要，并问：接下来是继续细化、**落盘定稿**、**拆成小项落盘**、还是（小需求）直接开始实现？

范围明显偏大、跨多个可独立交付面、或用户表达怕一次做太大时，应**主动提议**拆切片，而不是默认整包开干。

## 「已澄清需求」模板

用简洁列表，不要空话：

```markdown
## 已澄清需求
- **要解决什么**：
- **谁用 / 在什么场景**：
- **范围内**：
- **明确不做**：
- **验收标准**（可观察行为）：
- **风险 / 已知取舍**：
- **仍待决**（若有）：
```

## 切片（大需求拆小）

在定稿已清、用户同意拆项之后做。原则：

- **垂直切片**：每项尽量可单独验收（可观察行为），避免「只建表 / 只改 UI」这种无法单独验证的横切，除非用户明确要
- **有序**：标明依赖（谁必须先做）；无依赖的可并行但默认仍按清单顺序
- **小而完整**：单项不应大到难以 review；也不要碎成无法独立理解的微步骤

模板（落盘或聊天均可）：

```markdown
## 切片清单
- [ ] **S1** …（验收：…）（依赖：无）
- [ ] **S2** …（验收：…）（依赖：S1）
```

默认与定稿同主题：`.scratch/requirements/<主题>.slices.md`（也可写在定稿文件末尾「切片清单」节，听用户的）。开干口令示例：「做 S1」「按 slices 做下一项」。

## 落盘（定稿摘要）

聊天里的摘要是过程稿；下列情况应**提议落盘**（先问路径/文件名，用户同意后再写）：

- 用户说「落盘」「写成 plan」「定稿」「记下来」「拆成小项落盘」
- 收束时用户准备开干、换会话，或同意切片
- 讨论已多轮且出现明显改口，继续只靠聊天容易丢结论

默认路径：

- 定稿：`.scratch/requirements/<简短英文或拼音主题>.md`
- 切片：`.scratch/requirements/<同主题>.slices.md`（若拆了）

目录名已含 `requirements/`，文件名不再重复该词；点号让同主题的定稿与切片相邻排序，读作同一份的变体。

`.scratch/` 已 gitignore，仅本地。定稿用「已澄清需求」模板；已有文件则**整份更新为最新定稿**，并在文首可加一行「上次更新：YYYY-MM-DD」。

`.scratch/requirements/` 的定稿与切片是**一次性脚手架**：实现期间只在切片上打勾，切片做完即作废（用户自己会删）。不要回头补内容或补记变更，除非用户点名要改。

开干时优先让用户指向定稿/切片文件或点名编号；实现以落盘为准，不以早期聊天回合为准。

## 提问时可对照的维度（按需，勿整表抛出）

心里过一遍与当前需求相关的维度，**只把真正卡决策的问出来**：

- **范围**：改哪条产品线/模块；明确非目标
- **角色与权限**：谁能触发；鉴权/授权方式是否变化
- **数据**：存什么、谁拥有、隔离边界（多租户/多用户）；已上线需考虑存量数据，破坏性变更走迁移（见 `AGENTS.md`）
- **交互**：同步 vs 异步；要不要实时/流式反馈；失败与重试如何暴露
- **集成**：是否依赖外部服务、队列、定时任务、第三方 API
- **可观测与验收**：日志/指标；怎样算做完（可演示的行为）

若仓库有 `AGENTS.md`（或等价的仓库规则文件）与 `docs/` 等领域的文档，用它们校正问题，**不要**把文档整段念给用户。

## 语气

直接、短句；先对齐再发挥。不要用「很高兴帮你梳理需求」这类开场。
